# Changelog

One entry per released tag, grouped by minor. Latest first.

Pre-1.0 the surface is intentionally evolving — every release may
change something operators depend on. Read each entry before
upgrading across more than a few patches at a time. Releases
older than the first structured entry below live in the git log
and on the GitHub Releases page.

## v0.10.x

- v0.10.6 (2026-07-17) — **Restores background-daemon mode in the pre-built binaries and fixes a broad set of sync data-loss and recovery edge cases.** A correctness and hardening release. It restores `start --daemon` in the pre-built binaries (it silently never started a daemon while reporting success), refuses to enroll over plaintext HTTP so an API key and mTLS private key can no longer leak, and closes a broad set of rare but real sync-engine edge cases that could drop a delete, revert or destroy an un-uploaded edit, delete a just-recreated file, leak a file on the server, or wedge the client in a permanent catching-up state. Nested build and repository directories (a project checked out inside the synced folder) are now correctly ignored. No configuration changes are required. **Changed:** *Adopted newly hardened framework primitives* — The auto-update signature verifier, the metrics exposition renderer, the post-quantum TLS agent's group configuration (now validated), release-time version ordering, and several internal reads now route through the vendored framework's hardened primitives instead of local re-implementations, and the loopback-host and certificate-pin derivations are consolidated to single implementations. No behavior visible to operators changes. **Fixed:** *`start --daemon` works again in the pre-built binaries* — In the released single-file binaries the background daemon never actually started — the parent printed "Daemon started" and exited while the detached worker died immediately parsing its own path as a command, leaving a stale PID file and no syncing. It now starts correctly on every platform, and a worker that dies during startup is reported instead of masked as success. Running from source was unaffected. · *A failed auto-update install resumes syncing instead of going idle* — If an update download verified but the install step failed (for example an anti-virus scanner holding the binary open on Windows), the daemon stopped its sync engine for the swap and then, on failure, left it stopped — syncing silently ceased until the process was restarted. A failed install now restarts the sync engine (re-reading any live pattern changes) and continues on the running version, and the auto-update recovery path was hardened against several rare states that could roll a healthy update back or strand a partially-installed one. · *A delete is no longer silently undone by a single failed server request* — When a local delete's server request failed once (a transient network blip), the file was later re-downloaded by the recovery pass and reappeared on every device — the delete was dropped. A failed delete is now retried on its own rather than being mistaken for a failed download, and a delete for content the client never actually held (a download that never landed) is no longer propagated to the server. · *An un-uploaded local edit is preserved across a rename* — Renaming a file whose most recent edit had not yet reached the server (a failed or in-flight upload) could mark it as fully synced under the new name — so the edit was never sent — or, when the rename coincided with a remote change, overwrite the edit outright. The renamed file now keeps its pending upload so the edit is sent, and a colliding remote change preserves the local edit as a conflict copy. · *Deleting then quickly recreating a file no longer deletes the new file* — Recreating a file within a second of deleting it (common with tool-regenerated output) could let the buffered delete fire after the recreate's upload and remove the new file from the server. A same-path recreate now supersedes the pending delete, and the delete step additionally skips any path whose file has reappeared. · *Deleting a file mid-upload no longer leaks it on the server* — Deleting a brand-new file while its first upload was still in flight left the file on the server forever and a permanent stuck record locally. The vanished file is now recognized as a delete and removed from the server. · *The client no longer gets stuck in a permanent catching-up state* — After an event that could not be applied at the moment (a momentarily locked file), the change cursor could freeze for the rest of the session — the client reported catching-up indefinitely and its last-sync time went stale even though data was flowing. The cursor now clears once the delayed event finally applies, and a failed case-only rename no longer lets a later event skip past it. · *A temporarily-unreadable synced folder no longer deletes everything* — If the synced folder itself became briefly unreadable — an unmounted network or removable volume — every tracked file looked deleted and those deletes could propagate to the server and every device. Local deletes are now ignored while the synced folder is unreadable and reconsidered once it returns. · *A project checked out inside the synced folder is correctly ignored* — The default ignores for repository and build directories (.git, node_modules, __pycache__, and similar) only applied at the top of the synced folder, so a project cloned into a subfolder uploaded its entire .git and node_modules trees. These directories are now ignored at any depth. Ignore and include patterns also now accept a Windows-style backslash separator and match regardless of Unicode composition. · *Smaller correctness fixes* — A crash-interrupted upload is now actually re-sent by the recovery pass rather than silently skipped; shutdown waits for in-flight downloads before closing so it no longer logs spurious errors; a manually-entered API key is trimmed and an empty one refused; the credential file is read without a race that could report a spurious error during a concurrent re-enrollment; and a routine save-then-delete during hashing no longer logs at error level. **Security:** *Enrollment refuses plaintext HTTP to a non-loopback server* — The enrollment exchange sends your enrollment code and receives your API key and mTLS private key. Over plaintext http:// to a non-loopback host these travelled in the clear, and the existing refusal only ran later when the daemon started — after the credentials had already been exposed. Enrollment now refuses a non-loopback http:// server before sending anything. A loopback address (a TLS-terminating sidecar) is still allowed, and HERMITSTASH_ALLOW_PLAINTEXT=1 remains the explicit opt-out. · *Lookups keyed on untrusted names reject inherited object members* — Several internal lookups (log level, license identifier, changelog heading, configuration keys) resolved a name against a table without an own-property check, so a name matching a built-in object member could slip a validation. All now use own-property checks. A support-bundle credential scrub also matches the authorization scheme case-insensitively, and an in-string bearer-token detector now redacts a credential embedded in a log message in the live log and on standard output, not only in the support bundle. **Supply chain:** *Vendored framework advanced to blamejs v0.17.11* — Carries upstream security and correctness fixes across the wire, crypto, and process layers, including a DER decoder that rejects a non-minimal length encoding (closing a parser differential under every certificate parse), a WebSocket client that connects to wss:// hosts given as IP literals, a shared HTTP cache that no longer serves an authenticated response across principals, safe-decompression that refuses an unknown algorithm instead of returning input unchanged, and a family of lookup guards that reject prototype-member names. · *Refreshed the pinned GitHub Actions* — The commit-pinned actions in the release and container-publish workflows were advanced to their current releases (still pinned by commit hash with a version comment). **References:** [blamejs framework](https://github.com/blamejs/blamejs)

- v0.10.5 (2026-07-03) — **Stops spurious conflict copies on multi-device edits and fixes several sync-recovery and lifecycle edge cases.** A correctness release. It stops the client from creating (and fanning out) a spurious conflict copy when another device edits a shared file — the single most common multi-device operation — closes a rare case where a locked local file during catch-up could let a server-side delete be missed, keeps a certificate renewal from aborting an in-progress transfer, ensures a background daemon's final error line reaches its log file, and makes enrollment fail clearly when the server returns no API key. No configuration changes are required. **Fixed:** *Editing a shared file on another device no longer creates a spurious conflict copy* — When another device changed a file and the server broadcast the replacement, a receiving device that still held the previous synced version incorrectly treated it as a local divergence — writing a .conflict copy of the already-synced content and then, because that copy looks like a new local file, uploading it so the junk propagated to every device. The client now recognizes the un-diverged previous version and skips the conflict copy; a genuine local edit made before the remote change is still preserved as a conflict copy exactly as before. · *A locked local file during catch-up no longer lets a server-side delete be missed* — If a remote delete arrived for a file the client could not read at that moment (locked or unreadable), it correctly kept the file and left the change for a later retry — but a subsequent catch-up reconnect could advance the change cursor past the un-applied delete, so it was never re-delivered and the file lingered with a stale record. The catch-up recovery now refuses to advance past an event that failed to apply, leaving a visible, self-healing stall until the file is readable again. · *A certificate renewal no longer aborts an in-progress transfer* — When the client rotated its mTLS credentials (on renewal or a CA rotation) it replaced its connection pool and destroyed the previous pool on a fixed 30-second timer — which could cut off a large upload or download still running on an existing connection. The previous pool is now closed only once its in-flight transfers finish (bounded by the existing per-transfer ceiling), so a healthy transfer completes across a credential rotation. · *A background daemon's final error line now reaches its log file* — When the daemon exited on a fatal startup or authentication error, it wrote the final diagnostic and terminated before the asynchronous file logger had flushed, so that last line was lost from the rotated log — a daemon's primary post-mortem record. Those exit paths now flush the log (bounded) before exiting. · *Enrollment fails clearly when the server returns no API key* — The interactive and headless enrollment flows assumed a successful response always carried an API key. A success response without one (for example a certificate-reissue code sent to the enrollment path) is now rejected with a message that points to the repair command, instead of storing an empty credential and failing opaquely later.

- v0.10.4 (2026-07-03) — **Hardens the container build and the systemd / Podman / Kubernetes / Unraid deployment paths.** A deployment-surface release. It digest-pins the container build's verify stage (closing a path where a republished base tag could ship a backdoored signed binary), fixes the systemd auto-updater so it actually rolls back when a new binary won't start, stops the installer from overwriting an operator-edited update config, and tightens the Kubernetes and Unraid references. The client binary and its behavior are unchanged; these are build- and deploy-layer fixes. **Changed:** *Kubernetes manifest drops the service-account token and re-pulls a rebuilt image* — The reference Deployment is outbound-only and never calls the Kubernetes API, so it now sets automountServiceAccountToken: false — removing a default credential a compromised client could use for lateral movement. Its imagePullPolicy is now Always (instead of IfNotPresent) so a rebuilt, security-patched :latest is re-pulled on restart; pin the image to a @sha256 digest in your overlay for a reproducible, cosign-verifiable deployment. · *Unraid template drops the ineffective PUID/PGID variables* — The container runs as a fixed non-root user (uid:gid 1000:1000) by design, so the template's PUID/PGID variables were silently ignored. They have been removed; set your appdata and synced host folders to owner 1000:1000 (or group-writable for gid 1000) instead — the template descriptions now say so. **Fixed:** *The systemd auto-updater rolls back when a new binary won't start* — The external updater (deploy/update.sh) restarts the service after swapping in a new binary, then health-checks it. Under `set -e`, a restart that returned non-zero — exactly what happens when the new binary crash-loops or never signals ready — aborted the script before the rollback ran, leaving the broken binary installed and the daemon down. The restart no longer aborts the script; the health probe decides, and an unhealthy start now rolls back to the previous binary as intended. · *Reinstalling no longer overwrites your updater configuration* — Re-running deploy/install.sh reset /etc/default/hermitstash-sync-update to the shipped all-commented default, silently discarding an operator edit such as a paused auto-update. The installer now writes that file only when it is absent; on an upgrade it drops the shipped template beside it as a .new file to diff, leaving your configuration intact. · *The installer prints an actionable hint when it can't resolve the latest release* — If the GitHub API call that resolves the latest version failed (for example an unauthenticated rate-limit), `set -e` aborted the installer before its 'set VERSION=X.Y.Z to pin' guidance could print. The resolve step no longer aborts, so the actionable message is shown. · *The Podman runner waits for first-run enrollment before handing off* — On first run, deploy/podman.sh enrolled inside a bootstrap container and then replaced it with a Quadlet unit that carries no enrollment code. If enrollment hadn't finished writing its config to the volume in that window, the Quadlet container crash-looped as unconfigured. The runner now waits (bounded) for the config to be persisted — or for a failed enrollment to surface — before the hand-off. · *Uninstall removes a leftover in-progress update binary* — deploy/uninstall.sh removed the installed binary and its rollback copy but not a `.new` staging file left by an update interrupted mid-swap. That file is now swept as well, and the updater clears a stale `.new` on exit. **Security:** *The container build's verify stage is digest-pinned* — The two-stage image build runs the SHA3-512 + ECDSA signature check — and materializes the binary copied into the runtime image — in a first stage based on node:24.18.0-slim. That base was a mutable tag while the runtime base was already digest-pinned, so a republished base tag could have run attacker code in the verify stage and shipped a backdoored binary that then carried a valid cosign signature and SLSA attestation. The verify-stage base is now pinned to an immutable digest, on the same refresh cadence as the runtime base.

- v0.10.3 (2026-07-03) — **Restores Linux/macOS self-update, hardens sync recovery, config validation, and the support bundle.** A correctness and security release. It restores in-daemon self-update on Linux and macOS, makes the Node.js version gate actually enforce its floor, stops a reconcile pass from overwriting a newer local edit with the server's older copy, ends several transfer-retry and reconnect loops, refuses a plaintext non-loopback server URL, closes support-bundle information leaks, and emits a schema-valid release SBOM. No configuration changes are required, though maxFileSize in config.json is now enforced. **Changed:** *maxFileSize in config.json is now enforced* — The maxFileSize setting, previously accepted but ignored, now refuses a file larger than it before an upload or download begins. It can only lower the built-in per-file ceiling (HERMITSTASH_MAX_FILE_BYTES, default 256 GiB), never raise it. If you set a non-zero maxFileSize expecting it to have no effect, files above it will now be skipped with an actionable error. **Fixed:** *In-daemon self-update installs again on Linux and macOS* — The self-replace step now passes the verified SHA3-512 of the downloaded binary to the install call, which recently began requiring it. Without the hash the call was rejected before any file was touched, so a bare-binary daemon downloaded and verified an update but silently never installed it. Windows now also re-hashes the downloaded binary against the verified digest immediately before it replaces the running image. · *The Node.js version gate now enforces the 24.18.0 floor* — The startup check that refuses to run on an unsupported Node.js parsed the running version with a pattern that never matched the real version string, so it always fell through and enforced nothing. It now parses the version correctly and refuses to start below 24.18.0 with an actionable message. Prebuilt binaries embed a matching runtime and are unaffected. · *A stranded local edit is no longer overwritten by the server's older copy* — After an upload exhausted its retries, a later reconcile pass could re-download the server's older version over the newer local edit. The reconcile path now preserves the local bytes as a conflict copy first — the same protection the live-change paths already apply — so an edit that outran a failed upload is never lost. · *Over-cap files and permanently-rejected transfers are no longer retried every cycle* — A file larger than the effective per-file limit, or an upload the server permanently rejects, was re-attempted on every reconcile pass indefinitely. Such a transfer is now recorded once and skipped until a later success or a reconnect, ending the repeated wasted requests and error-log noise. · *A stalled catch-up no longer reconnects in a loop* — When a change at the top of a catch-up batch could not be applied (a locked or unreadable local file), the client could reconnect on every reconcile tick. It now reconnects to advance the cursor only when a pass actually recovered stranded data, so an unappliable change no longer drives an endless reconnect loop. · *Bandwidth and concurrency limits above ~2 GB/s are no longer silently disabled* — The upload/download rate limits and the upload-concurrency setting were coerced with a 32-bit truncation that wrapped a value at or above 2^31 to a negative number, silently disabling the limit or clamping concurrency to one. They now use the full integer range. · *The support bundle no longer leaks the home-directory path or a credential* — The diagnostic support bundle could include the absolute state-database path (revealing the OS user and home layout) and, in a free-form log line, a bearer credential. The path is now reduced to a basename, a bearer token is redacted by shape, and secret literals containing quotes or backslashes are matched in both their raw and JSON-escaped forms. · *Config.json validation is stricter and clearer* — A config.json whose top level is not an object, or whose server / bundle / share / folder fields are the wrong type, is now rejected at load with a message that names the real problem instead of failing opaquely later. **Security:** *Plaintext http:// to a non-loopback server is refused* — A plaintext http:// server URL disables TLS, mTLS, and the post-quantum group pinning, sending the API key and all traffic in the clear. It is now refused at config-load for any non-loopback host. A loopback target (a TLS-terminating sidecar on the same host, or a dev target) stays allowed; a deliberate non-loopback plaintext hop now requires HERMITSTASH_ALLOW_PLAINTEXT=1. **Supply chain:** *The release SBOM is now a schema-valid CycloneDX 1.6 document* — The generated CycloneDX SBOM placed externalReferences on a lifecycle entry, which the 1.6 schema forbids, so every release shipped a technically-invalid document. The references now sit on a valid component, so CycloneDX-aware scanners parse the SBOM cleanly. · *The release and image pipelines pin their remaining tool downloads* — The container-image build and code-scanning workflows now pin the vulnerability scanner and workflow linters to verified versions (with a checksum on the scanner binary) rather than a floating latest, and the image build checks out the exact commit its provenance names. This closes the gaps where a compromised upstream tool release could enter a privileged build step.

- v0.10.1 (2026-07-03) — **Refreshes the vendored framework and raises the Node.js floor to 24.18.0.** A maintenance release. It refreshes the vendored cryptography and networking framework to its current release — picking up its hardening for WebSocket, HTTP, JSON, path, and regex handling — raises the minimum Node.js runtime to 24.18.0, and keeps the self-update flow working under the framework's stricter release-asset pattern check. No configuration changes are required. **Changed:** *Refreshed the vendored cryptography and networking framework* — The vendored framework the client is built on was updated to its current release. The refresh brings its security hardening for the outbound WebSocket client, HTTP responses, size- and depth-capped JSON parsing, path-traversal-safe file resolution, and regular-expression safety — the primitives the client relies on when talking to a server. · *Minimum Node.js runtime raised to 24.18.0* — The runtime floor is now Node.js 24.18.0 (24.17.0 was a security release; 24.18.0 bundles SQLite 3.53.1 and a backup-path fix). Prebuilt binaries embed a matching runtime; only from-source installs need to act. **Fixed:** *Self-update keeps working under the framework's stricter asset-pattern check* — The framework now runs the release-asset match pattern through its ReDoS-safe regular-expression sanitizer. The pattern that selects this platform's binary and signature is now expressed as a bounded character class rather than an optional group with an inner quantifier — a shape the sanitizer refuses. Without this change the refreshed framework would have rejected the pattern and silently disabled self-update; stable, prerelease, and build-metadata release names all continue to match, and the wrong-platform and ML-DSA sidecar assets are still excluded. **Migration:** *Run Node.js 24.18.0 or newer for from-source installs* — Upgrade the runtime to Node.js 24.18.0+ before running the client from a source checkout. Prebuilt binary releases embed their own runtime and need no action.

- v0.10.0 (2026-06-25) — **Extends the from-source startup integrity check to the framework's transitive bundles and emits strictly-valid SBOM package URLs.** A supply-chain and startup-integrity release. The from-source startup check that verifies each vendored dependency against its recorded hash now also covers the framework's executable transitive bundles, which previously could execute before any check ran, and it refuses to start if the manifest has been stripped of everything to verify. The release SBOM now percent-encodes its Package URLs so a strict validator accepts them. Prebuilt binaries skip the startup check and are unaffected. No configuration changes are required. **Security:** *The from-source startup integrity check now covers the framework's transitive bundles* — Running the client from a source checkout verifies each vendored dependency file against the SHA-256 hashes recorded in the manifest, before the framework is loaded, and refuses to start on a mismatch. The check covered the framework's own files and two cryptographic bundles but not the other transitive bundles the framework executes at startup (elliptic-curve, PKI, and WebAuthn helpers) — a tampered one of those could have run before any check. Those bundles are now hashed by the same pre-load check, so a corrupted or tampered transitive bundle is refused first. Their hashes were already recorded for the SBOM; this puts them behind the gate. Prebuilt binaries skip this check and are unaffected. · *Startup refuses to continue if the integrity manifest has nothing to verify* — If the integrity manifest were stripped of its file and hash entries — a botched dependency refresh, a partial clone, or tampering — the startup check would previously verify zero files and pass silently. It now treats verifying nothing as a failure and refuses to start with an actionable message, so a manifest that lost its coverage is caught rather than waved through. **Supply chain:** *Release SBOM package URLs are percent-encoded* — A component whose version string contained spaces or parentheses produced a Package URL (purl) with those characters left unencoded, which a strict purl validator rejects as malformed. Version components are now percent-encoded per the purl specification, so every component's purl in the release SBOM is syntactically valid. A normal semantic version is unchanged.

## v0.9.x

- v0.9.21 (2026-06-25) — **Refuses a symlink when reading logs into the support bundle and corrects several CLI exit-code, redaction, and enrollment edge cases.** A robustness and hygiene release for the command-line surface and the diagnostic bundle. The support-bundle log read now refuses a symlink, matching every other read in the diagnostics module, so a link planted in the log directory cannot redirect an arbitrary file into the bundle. The stop and resync commands now report a non-zero exit code when they fail to act, so shell automation that gates on the exit code behaves correctly. Following the log live (log --follow) no longer prints stray NUL bytes or loses content when the log rotates. An incomplete certificate set from the server during enrollment is now surfaced as an error instead of silently doing nothing, and an init failure routes its message through the same secret-masking path as every other fatal error. No configuration changes are required. **Fixed:** *The stop and resync commands report a non-zero exit code when they fail* — When the daemon could not be stopped (for example a permission error killing the process) the stop command still exited zero, so a script of the form "stop && next-step" proceeded as though the daemon had stopped. Likewise resync exited zero when the signal could not be delivered or on a platform where it is unsupported. Both now set a non-zero exit code on a genuine failure, while the benign "no daemon running" case stays zero. · *Following the log live no longer prints NUL bytes or loses content across a rotation* — When the log rotated while "log --follow" was running, the follower could emit a run of NUL bytes and then stall, missing the new file's content, because it wrote a full read buffer regardless of how many bytes were actually read and advanced its position to a stale size. It now writes only the bytes read, advances by that amount, and re-follows from the start of the fresh file when a rotation shrinks it. · *An incomplete certificate set during enrollment is surfaced as an error* — If the server returned only some of the three mutual-TLS certificate fields (client certificate, key, and CA), enrollment silently wrote nothing and reported success, leaving any prior certificates in place — a later connection would then fail authentication with no hint why. A partial set is now reported as an enrollment error; a response with no certificate fields at all is still treated as an intentional API-key-only enrollment. The comment describing the certificate write was also corrected: the three files are each written atomically but not as a single transaction, so a torn set is recoverable by re-running init or repair. **Security:** *The support bundle refuses a symlink when reading a log file* — Every read in the diagnostics module refuses to follow a symlink, except the support-bundle log read, which used a symlink-following call. A symlink planted in the log directory under a rotation-shaped name was therefore followed and its target read into the bundle (CWE-59), defeating the "only log files" contract — the bundle's redaction only masks known secret shapes, so an arbitrary target could leak. Log files are now enumerated and read with the same symlink-refusing path as the rest of the module; legitimate rotations are unaffected. · *An init failure message is masked through the same redaction path as every other fatal error* — A failed init printed its error text straight to standard error, bypassing the secret-masking barrier that every other fatal exit routes through. A server that echoed a secret-shaped value back in an error would have landed it unmasked. Both the interactive and non-interactive init failure paths now go through that barrier. **Supply chain:** *Vendored blamejs framework updated to 0.15.26* — The vendored blamejs framework is updated to 0.15.26. The upstream changes are a worker-thread handle-leak fix in a sandbox primitive this client does not use and internal test-harness corrections; no primitive this client consumes changed. The release SBOM's component version and the recorded per-file dependency hashes are regenerated to match.

- v0.9.20 (2026-06-25) — **Restores auto-update on GitHub's current release CDN and hardens remote-delete and download handling against data loss.** A reliability and integrity release for the auto-update and sync data paths. GitHub moved its release-asset content delivery network, and the in-binary self-update only permitted the previous host — so a bare-binary install with auto-update enabled silently stopped installing updates; the egress allowlist now covers GitHub's content CDN by domain suffix and survives a future CDN rename. A remote delete that arrives for a local file the client cannot hash (one that grew past the configured size ceiling, or became a special or unreadable file) is no longer honored by destroying that file; the client keeps it and retries once it can be verified again, and the same protection covers a remote overwrite. A file the server renames into the synced scope without re-sending its checksum is now size-verified before it is committed. No configuration changes are required; bare-binary installs on auto-update resume updating automatically. **Fixed:** *Auto-update works again on GitHub's current release CDN* — The in-binary self-update (used by bare-binary installs with auto-update enabled) downloads each release asset from github.com, which redirects to GitHub's signed content CDN. GitHub moved that CDN to a new hostname, and the updater's egress allowlist only permitted the previous one, so the redirect was refused and the update silently never installed — the daemon stayed on its current version while logging only a warning. The allowlist now matches GitHub's content CDN by domain suffix, covering both the previous and current hosts and a future rename, so auto-update resumes. The release signature check (P-384 ECDSA over the SHA3-512 digest, verified against the in-binary public key) remains the integrity gate before any swap. Systemd, Docker, Podman, and Kubernetes installs were unaffected — they update through their own mechanisms. · *A remote delete no longer destroys a local file it cannot verify* — Before honoring a server-side delete, the client hashes the local file to check whether you changed it independently (in which case it keeps your copy as a conflict file). If that hash could not be computed — the file had grown past the configured size ceiling, or had become a special or unreadable file — the client could not confirm the file was unmodified, yet it deleted the file anyway, losing locally-changed bytes with no conflict copy. It now keeps the file and its tracking row and re-tries the delete on the next reconnect once the file is verifiable again. The conflict-copy path that protects a local file from a remote overwrite is hardened the same way. **Security:** *A file received without a checksum is size-verified before being committed* — Every downloaded file is verified against its SHA3-512 checksum before being written into place. On one selective-sync edge — when the server renames a file from a path you do not sync into one you do, and omits the checksum because the content is unchanged — the client had no checksum to verify against and committed the bytes unconditionally, so a truncated or corrupt response body could land marked as synced. The exact byte count is now compared to the size the server declared, and a mismatch is refused. The transport is already PQC TLS 1.3 with mutual authentication, so this closes the residual gap of a half-failed response body rather than an active attacker.

- v0.9.19 (2026-06-25) — **Recovers a stalled file watcher on a config reload, protects local sync state during shutdown, and validates the auto-update setting.** A reliability and safety release for the file watcher and configuration paths. A file watcher that gave up after a sustained change storm can now be brought back by editing the ignore patterns and reloading, instead of requiring a full restart; a folder excluded by its path (without a trailing /**) now also prunes the polling scan, so a large excluded folder no longer overflows the watcher. A reload signal arriving during shutdown can no longer clear the local sync database or re-open the server connection mid-teardown. The auto-update setting is now validated at startup: a non-boolean value such as a quoted "false" previously passed silently and left the in-binary self-replace path enabled — the opposite of the intent — and is now rejected with an actionable message. A malformed (non-string) ignore or include entry no longer aborts a live config reload. Operators who set autoUpdate to a quoted string must change it to an unquoted true or false; no other action is required. **Fixed:** *A file watcher that exhausted its restart attempts can be recovered by a config reload* — If the file watcher hit a sustained event storm and used up its automatic restart attempts, it stopped detecting local changes until the daemon was restarted — even though the error advised narrowing the ignore patterns and reloading. Editing the ignore patterns and sending a reload now re-arms the watcher, so the advised remediation works without a full restart. The reload also triggers a fresh scan so any change made while the watcher was down is picked up. · *Excluding a folder by its path now prevents a watcher overflow on large trees* — An ignore entry written as a folder path without a trailing /** (for example data/cache) already excluded that folder from sync, but it was not used to prune the polling file-walk, so a very large excluded folder could still push the per-scan file count past the watcher's ceiling and stop change detection. backoff* — On WebSocket drops the client backs off from 1 second up to a 5 minute ceiling, preventing reconnect storms against the server while staying responsive on transient blips. · *Initial sync plus catch-up via `seq` cursor* — Bootstraps a new bundle by walking the full file list, then on every later connect replays missed changes from the last acknowledged sequence number forward. · *Single-binary distribution via Node.js SEA* — Ships as a Node.js Single Executable Application so operators install one signed binary per platform with no separate runtime install required. **Migration:** *Requires HermitStash server v1.3.0 or newer* — The sync bundle type, `/sync/ws` endpoint, and `seq`-cursor catch-up flow this client depends on land in server v1.3.0; older servers will reject the WebSocket upgrade.
